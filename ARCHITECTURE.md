# Архитектура v2

## Не переписывать работающий цикл ради несовпадающего промпта
Фактический проект: FastAPI/Starlette, requests/httpx, один Python worker,
SQLite. Aiogram раньше не использовался, Telegram нужен только для тревог.
Сохранены прежние роуты, исправления CSRF/proxy в web_security.py и роли.

`Engine(FazerMixin, LegacyEngine)` — совместимый публичный сервис заказов.
`commerce.py` реализует новую выдачу. `engine.py` содержит импорт/чат и старую
историю. `worker.py` запускает очередь, обработку сообщений, GET-проверки,
каталог, поднятия, уведомления и резервные копии. Фоновые сетевые операции не
выполняются в обработчиках GET админки.

## Адаптеры
`FazerClient.buy_item(service,payload,idempotency_key) -> dict order`
`FazerClient.check_order_status(order_id) -> dict order`
`FazerClient.get_balance() -> int USD micro-units (1 USD = 1_000_000)`

В `adapters/fazer.py` есть native-async `AsyncFazerClient` и отдельные
`FazerCardsUCAdapter` / `FazerCardsStarsAdapter` с buy_item/check_order_status/
get_balance. Они только транспорт: **нельзя вызывать Stars.buy_item напрямую
из обработчика FunPay и рассчитывать, что переданный ключ сам устранит дубли**.
Для интеграции нового asyncio-диспетчера использовать:

```python
from autoucbot.dispatcher import AsyncOrderDispatcher
payments = AsyncOrderDispatcher(engine)
# После сохранения оплаченного заказа, выбора получателя и подтверждения:
await payments.buy_item(funpay_order_id)
await payments.check_order_status(funpay_order_id)
balance_micro_usd = await payments.get_balance()
```

Диспетчер передаёт работу существующему журналируемому Engine через to_thread.
Отмена ожидающей coroutine не означает отмену покупки; повторный вызов читает
состояние того же заказа. Прямой Fragment/TON адаптер не регистрируется.

## Схема 2 и значения
Исходные таблицы сохраняются. orders/products.service = uc|stars;
supplier = gamecore|fazer. Старое orders.uc теперь количество единиц соответствующего
направления, а не смешанная сумма. Интерфейс и статистика разделяют UC и Stars.
products.sku_uc — единицы в позиции API, multiplier — позиций на лот FunPay.
Для Stars API-каталог имеет единицу 1 Star, multiplier = 50/100/…;
в покупку отправляется агрегат quantity = multiplier × купленные лоты.
Для UC каждая фактическая API-операция имеет отдельную строку fazer_parts.

fazer_skus связывает локальный SKU >= 1_000_000_000 с category_id/offer_id.
fazer_parts содержит неизменяемое тело, его SHA256, отдельный Idem-key, статус,
provider_id, USD-цену, резерв, подтверждённую цену и зафиксированный курс.
fazer_wallet — последний фактический USD-остаток. Цены Decimal, хранение микродолларов.
Округление Stars выполняется после умножения количества. RUB — целые копейки.
В карточке видно, является ли себестоимость оценкой или подтверждённой суммой.

## Инварианты
1. Уникальный FunPay order ID, не чат/UID/цена, определяет оплаченную покупку.
2. Повтор одного события идемпотентен; два разных оплаченных ID — две покупки.
3. До POST транзакционно фиксируются body+hash, попытка и состояние sending.
4. sending при падении превращается в unknown; неизвестный POST не повторяется.
5. Для UC дополнительно отправляется документированный Idempotency-Key.
   У Stars поддержка этого заголовка не подтверждена: он намеренно не отправляется.
6. Перед каждой частью повторно читается оплата/состав заказа, получатель,
   активность товара, цена, баланс с общими резервами, лимиты и подписка.
7. Весь состав резервируется до первой выдачи; pending/unknown остаются
   консервативно зарезервированными даже после возможного списания у поставщика.
8. webhook только ускоряет GET по известному provider_id. Совпадение суммы,
   времени и username не используется для автоматической привязки пропавшего ответа.
9. failed/refund не равен подтверждённому возврату денег. После сверки владелец
   может зафиксировать чистый фактический расход и объяснение в журнале.
10. Неизвестный результат блокирует направление; нехватка общего баланса может
    остановить оба. Уже отправленные операции продолжают проверяться, кроме
    явной заморозки всей установки при переносе.

## Миграция
Схема обновляется транзакционно, со снимком старой непустой базы. Мастер-ключ не
меняется. Экспорт замораживает источник под engine.lock и включает env-секреты
в зашифрованное хранилище базы. manifest + SHA256 базы подписаны производным
ключом APP_SECRET. В архиве нет самого APP_SECRET; данные заказов не зашифрованы.
Импорт только offline, с проверкой HMAC, размера, путей, целостности и ключа.
После импорта observe, paused, recovery_required, сброшенные сессии.
Local flock НЕ распределённая блокировка: старый сервер обязательно остановить.

## Известные ограничения
Рабочая совместимость FunPay зависит от неофициального веб-интерфейса.
Не все ответы поставщика содержат финансовую детализацию; оценка не маскируется
под подтверждённое списание. Нет гарантии цена-запроса = цена-списания: API не
документирует max_charge, владелец явно принимает это и задаёт запас/лимиты.
Один экземпляр/процесс/диск; горизонтальные реплики запрещены.
