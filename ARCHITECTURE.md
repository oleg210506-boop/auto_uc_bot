# Архитектура / передача следующему разработчику

## Состав

Один Python-процесс: Uvicorn/FastAPI/Jinja web + один background worker thread. SQLite WAL на постоянном Volume; нет Redis, платной БД, фронтенд-бандла, CDN или браузера в runtime. Внешний I/O поставщика/FunPay обычно выполняется в worker, кнопки ставят долговечные задачи. Панель — HTML-формы и запросы по требованию.

- `config.py`: начальные переменные, строгие настройки, шаблоны сообщений.
- `db.py`: схема v1, транзакции, копии, аудит; денежные поля таблиц — **целые копейки**.
- `security.py`: vault из APP_SECRET, scrypt/TOTP, подписи вебхуков.
- `adapters/gamecore.py`: независимый REST-клиент, фиксированный origin, контракт/классификация ошибок.
- `adapters/funpay.py`: независимый неофициальный клиент сайта. Не выдавать за официальный API.
- `adapters/demo.py`: локальная персистентная симуляция; никаких сетевых запросов.
- `engine.py`: предметная логика; изменения под RLock и/или BEGIN IMMEDIATE.
- `worker.py`: задачи, сканирование/опрос, outbox, Telegram, изменение лотов, обслуживание.
- `web.py`: вход/права/CSRF, серверная панель и signed webhook.
- `web_security.py`: нормализация внешнего origin, HMAC-токен входа, диагностика CSRF; не имеет доступа к поставщикам или базе.
- `maintenance.py`: исключительно offline/startup restore, single-instance lock, принудительная сверка.
- `templates/`, `static/`: адаптивная панель; никаких клиентских API-ключей.
- `tests/`: изолированные базы, сетевые заглушки, запрет socket.create_connection.

## Жизненный цикл заказа

`awaiting_uid → awaiting_confirmation → ready → processing → completed`.

Особые состояния: `observed`, `manual`, `waiting_balance`, `unknown`, `partial`, `failed`, `cancelled`.
Заказы привязаны к режиму demo/live; Observe читает live, но не закупает/не отправляет/не изменяет FunPay.
Бизнес-статус заказа не подменяет фактические статусы `batches` и `provider_orders`.

Одна исходная партия = один SKU с количеством `product.multiplier × order.quantity`. GameCore может разбить один POST на несколько кодов; сохраняются и проверяются **все**. Поддерживается точный фиксированный номинал, `id_only`, RUB, необходимые строковые deliveryData.

Снимок товара/цены продажи фиксируется на оплаченный заказ. Перед POST повторяются проверки оплаты и состава заказа, доступности SKU, достаточности всей суммы/лимитов/минимальной маржи. Изменение текущего товара не переписывает оплаченный состав.

## Платёжные инварианты

1. Сообщения покупателя не подтверждают оплату. Только данные FunPay; собственный seller_id, настоящий buyer/chat, точное структурированное количество и allow-list метки/подраздела.
2. UUID-ключ и точное тело POST сохраняются до отправки. Дубли событий не создают новую партию.
3. HTTP timeout/5xx после отправки = **unknown**, не failed. Никакой новой покупки на новом ключе.
4. GameCore удерживает ключ не бессрочно; локальный консервативный рубеж повтора 23 часа. Слепое повторение неизвестной операции запрещено и до этого рубежа. Сначала сверка истории по externalOrderId.
5. Принятие POST не означает выдачу. Подтверждение по позициям; failed-parent может иметь completed-children. Частичная выдача не повторяется полностью.
6. Резервирование денег — локальное; provider source-of-truth для списания. После неизвестного запроса запрещена пересверка баланса поверх резерва.
7. У провайдера нет документированного потолка цены в POST. Локальные лимиты не защищают от резкого межзапросного изменения. Это явно подтверждает владелец до live.
8. Пауза закрывает новые закупки, но не опрос уже отправленных. Возврат на FunPay вручную не отменяет пополнение у поставщика.
9. Ручная финансовая форма только фиксирует доказанный результат; не выполняет внешних переводов. Не допускается при неоконченной/неизвестной партии.
10. Outbox записывается до отправки. Неизвестная доставка сообщения не повторяется автоматически.
11. Финансовую историю, seen_messages и использованные ключи не очищать «сбросом статистики». Исключение — только DEMO, отдельная защищённая операция.

## Баланс

`ledger` хранит локальные изменения в копейках. `set_balance` записывает дельту до **фактического полного** остатка и блокируется при незавершённых операциях. Повтор той же сверки не добавляет депозит дважды. Изменения вне autoUCbot не известны без API чтения остатка.

Фактический B2B GET баланса и числовое JSON-поле конфигурируются только после получения документации у GameCore. Ожидаем RUB. Несовместимую валюту/единицу измерения/схему нужно адаптировать и протестировать отдельно.

## Блокировки / перезапуск

`instance.lock` — Linux flock на том же диске на весь срок жизни worker. Оставлять один replica. Он **не защищает** от копии на другом диске.
При старте `sending` партии → unknown, `sending` сообщения → uncertain. Прерванные административные задачи не повторяются молча.

Restore копирует проверенную целостную SQLite-базу до запуска. Проверяет первоначальный APP_SECRET, делает страховочную копию текущей базы, убирает старые сессии/неотправленные сообщения. Live заблокирован до полной сверки пост-backup операций. Контрольная сумма уже применённой копии предотвращает повторный rollback на очередном restart.

## Расширение

Не добавляйте финансовые запросы в шаблоны или frontend. Нового поставщика реализуйте отдельным адаптером, не смешивайте статусы и currency. Внешний ключ идемпотентности не заменяет локальную историю.
Для изменений схемы вводите последовательные versioned migrations, обратную совместимость либо блокировку запуска; сохраняйте immutable payload/key старых партий. Текущий выпуск имеет schema_version=1 и не реализует будущие миграции.

Сначала контрактные тесты по актуальной документации и обезличенным ответам, затем контролируемая реальная приёмка. Не повышайте статус релиза до production только по количеству unit tests. Обновляйте constraints осознанно; Docker-сборка требует скачивания зависимостей из PyPI.
